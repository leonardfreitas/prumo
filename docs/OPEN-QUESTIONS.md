# Open Questions

Anything raised but not resolved. **This is the only home for an open question.** Review this file
at the start of every session.

A question is removed from here only when it is answered, and its answer goes to `DECISIONS.md`.

Entry format:

```
## <short name>

**Raised:** YYYY-MM-DD
**Question:** <what is unresolved>
**Why it matters:** <impact if we skip it>
**Blocks:** <which document or build-order step cannot be finished without it>
```

## Does RLS close the raw-SQL hole at an acceptable cost?

**Raised:** 2026-09-10
**Question:** Postgres Row Level Security is the only tenant guarantee that survives raw SQL and the
QueryBuilder. What does it actually cost in this stack?
**Why it matters:** the MikroORM filter is an application-level guard and its own documentation says a
raw query reads past it. Cross-tenant leakage is the highest-consequence silent failure in the project.
The known tension: RLS needs the tenant set per connection or per transaction, and transactions were
deliberately not wrapped around plain reads, so `SET LOCAL` has nowhere to live and a session-level
`SET` conflicts with transaction-mode pooling. Whether that has a clean resolution is unverified.
**Blocks:** nothing today; it would supersede part of `database/multi-tenancy.md`

## Does Prumo say anything about deployment?

**Raised:** 2026-09-14
**Question:** packaging, production environment variables, how migrations actually run in a pipeline, and the
orchestrator healthcheck: none of it is covered by any of the thirty-three documents.
**Why it matters:** every generated project needs it, and with no document each one invents its own. It was
raised by the template decision that deliberately omitted a `Dockerfile`: writing one would have meant deciding
base image, build stages, pnpm's role and the process user in code, with nothing behind them.
**Blocks:** nothing today. It is a candidate tenth area after V1.

## Does the CLI compose a multi-tenant form of a template?

**Raised:** 2026-09-14
**Question:** `templates/api` is written single-tenant. A multi-tenant project needs Better Auth's
`organization` plugin, the MikroORM filter registered `default: true`, its parameter set per request, and the
closed list of tenantless routes. Does the CLI wire that, or does the developer do it by hand from
`multi-tenancy/isolation.md`?
**Why it matters:** a forgotten filter is cross-tenant leakage, and it fails silently. Leaving it to hand
wiring is the one place the project would not fail closed. Wiring it automatically ships a filter registered
over **no tenant-scoped table**, because a day-zero multi-tenant project has none. `Profile` belongs to a
user, and `organization`, `member` and `invitation` belong to Better Auth. Both answers are defective today.
**Blocks:** nothing in V1, since it was decided on 2026-09-15 to ship the context only. It is the first item after V1, and
the wiring must not be switched by an environment variable: a wrong value would be cross-tenant leakage.

## Does a template carry a request-level test?

**Raised:** 2026-09-14
**Question:** should the API template include at least one test that sends a real HTTP request through the
Nest application, and does `core/testing.md` require that level at all?
**Why it matters:** an `import type` on a DTO makes `ValidationPipe` receive `Object` and validate nothing. It
passes lint, typecheck, build, boot and every service test. `core/tooling.md` now forbids it, but only a
request sending an invalid body and expecting 400 can catch it, and the template has no test at that level.
The same gap hides the guard, the filter and the serializer, none of which a service test touches.
**Blocks:** nothing today; it would add to `templates/api` and to `core/testing.md`

## How does `prumo update` refresh a project's `.prumo/`?

**Raised:** 2026-09-15
**Question:** a project generated by one Prumo version needs the knowledge-base corrections of the next. `INDEX.md`
and `config.json` are the tool's and safe to regenerate; everything else is prose the team owns.
**Why it matters:** overwriting erases the team's edits; not overwriting leaves the project on stale rules. It is in
effect a three-way merge over markdown.
**Blocks:** nothing in V1, which ships `prumo new` only.

## How does `prumo add` grow a project?

**Raised:** 2026-09-15
**Question:** adding a type to an existing project. Under the type-first decision, a second type turns `alone` into a
workspace: the app moves under `apps/`, the contract is extracted, the catalog is built.
**Why it matters:** it is composition applied to code the team already wrote, the riskiest operation Prumo could
perform on someone else's repository.
**Blocks:** nothing in V1, which ships `prumo new` only.

## Should the CLI refuse a project named after a dependency in its own tree?

**Raised:** 2026-09-17
**Question:** a four-type workspace generated with the name `ws` failed to install with `ERR_PNPM_IGNORED_BUILDS`
for `bufferutil` and `utf-8-validate`. `ws` is also the WebSocket library Expo depends on, and `pnpm why` listed the
workspace root, `ws@0.0.1`, as depending on them. The same workspace named `acme` installed cleanly.
**Why it matters:** the name is the first thing a user types, the failure names two packages the user never
chose, and nothing points back at the name. Any name that matches a package in the tree could do the same.
**Blocks:** nothing today. The known candidates are refusing names found in the resolved tree, which is only
known after installing, or keeping a short list of names the templates are known to pull in.
